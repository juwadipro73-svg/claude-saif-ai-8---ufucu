# SAIF AI private cloud builds — deployment template

This folder is a **template, not a deployed service**. The Android APK in this repository has no GitHub token, Drive credential, or service-account key. Its cloud actions fail closed until you deploy this gateway and a matching portal, configure the separately hosted Builder, and rebuild the APK with three public endpoint URLs. As of 2026-11-08, the separate `shahudgg/SaifAI-Builder` repository is public and draft PR #2 (`ba3d6e7`) is readable; the public download site still serves its demo instead of this gateway. Source access and passing local tests do **not** mean that a live cloud upload works.

## Private user file uploads from chat

APK, ZIP and common video files of any size up to **300 MB** (and supported images/text/PDF at **3–300 MB**) are staged **one file at a time**. Normal text and photos smaller than 3 MB stay in chat without a website link. The app retains the attachment draft on a failed upload, streams bytes rather than constructing a huge Base64 JSON value, verifies SHA-256, and creates a one-time website claim only after the owner-authenticated gateway copies the verified bytes into a private Drive folder. Files are not silently sent to the AI model for analysis.

`POST /api/push` takes Firebase Bearer + `X-Firebase-AppCheck` headers and a small JSON manifest, **not** `{data:"data:...;base64,...}`. Example:

```json
{"jobId":"123e4567-e89b-42d3-a456-426614174000","securityMode":"onetime","burnOnDownload":true,"files":[{"assetId":"123e4567-e89b-42d3-a456-426614174001","name":"App.apk","size":10485760,"sha256":"0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef","mimeType":"application/vnd.android.package-archive"}]}
```

The gateway returns `{jobId,ownerUid,uploadUrls:[{assetId,url}]}`. Upload the exact bytes to the signed `storage.googleapis.com` URL with a matching `Content-Type`, then call authenticated `POST /api/push/complete` with `{jobId}`. Only that same Firebase owner may finalize; the gateway checks the staged size/hash and Drive privacy, writes the private RTDB status, and returns a short-lived claim for its own `/download/<jobId>` page. A claim burns on download and can be refreshed from the signed-in app. Configure the Cloud Run request timeout for this potentially long GCS-to-Drive finalization (for example 30 minutes), and a private staging-bucket lifecycle rule to clean orphaned uploads. Small previews and this signed PUT are not public Drive links.

An authenticated `POST /api/trigger-build` also accepts the owner's `{ "prompt": "Build an app", "branch": "main" }` shape (optional `kind`: `apk`/`zip`/`video`), creates a tracked job ID and dispatches the **job_id-aware** builder. Firebase ID token and App Check headers are still required; this cannot magically make an incompatible prompt-only private workflow publish a finished file.

A generated **project ZIP** is also supported as a cloud job: the fixed builder prepares vetted Android sources and packages them with Python `zipfile`, excluding Gradle/build caches and symlinks. The template worker reports the private ZIP through the same callback and portal; it does not scrape arbitrary APKs or execute uploaded archives.

## Components

- `backend/`: Node 22/Cloud Run gateway. Requires Firebase Auth **and App Check** for job dispatch. Server alone holds the GitHub workflow-dispatch credential and private Drive read/write-to-its-folder credentials.
- `portal/`: Public download portal (React + Vite + Express). Deployed as the AI Studio project at `https://saifai-downloads.ai.studio/`. When `SAIF_CLOUD_API_BASE_URL` is set, it proxies vault queries and one-time claim downloads to the gateway; otherwise it serves a self-contained demo vault. Has its own `/healthz` for CI preflight.
- `builder-template/`: standalone example to **copy to the separate builder repository**; its `workflow_dispatch` builds Android debug APKs with a fixed Gradle template or renders simple MP4 timelines using FFmpeg, uploads results privately to Drive, and reports status to the gateway.
- `firebase/database.rules.json`: only a signed-in Firebase UID may read `apps/$uid`; clients cannot write status, read other users' jobs, or read the gateway's `cloudJobs` and quota records.

**Flow:** an authenticated Android account asks the backend to create a job → optional binary project assets are streamed to short-lived, private GCS signed upload URLs (no Base64 build archive) → the backend dispatches an Actions workflow on the builder repo → the worker reads the private job input, builds/renders, uploads to a private Drive folder and calls the authenticated gateway → the gateway checks the file's Drive parent and writes Firebase RTDB `apps/$uid/$jobId` → Android's job card receives status in real time and exposes a unique, file-specific link on **your website**: `https://YOUR-SITE/download/JOB_UUID#claim=ONE_TIME_TOKEN`. The job ID maps to exactly one verified private output; **the Drive ID is not in the URL, API link response or client-visible RTDB node**. The claim is in the URL **fragment**, which is not sent with the page request. The website checks it with a same-origin POST; its final button POSTs the claim to the backend, which consumes it atomically and **streams the private Drive file from your website**. The file stays in private Drive storage; the site serves it securely rather than uploading a public copy into its document root. There is no `uc?export=download` link and no website Google login. Claims expire after 10 minutes and can be refreshed by the same Firebase account in the app. A failed/interrupted stream consumes its claim; refresh the link in-app before retrying (range-resume is not part of this template).

## Before deployment

1. Use your own Firebase project, add the Android app/package in `app/google-services.json`, enable **Email/Password** and **Anonymous** Auth, and create a Firebase **Realtime Database** in your chosen region. From `cloud/firebase/`, apply the included rules with `npx firebase-tools deploy --only database --project YOUR_PROJECT_ID` after signing in as the project owner, then verify that unauthenticated clients cannot read `apps/` and user A cannot read user B. Register the Android application with **Firebase App Check / Play Integrity**. Play Integrity for sideloaded debug APKs may require additional configuration or fail; use a properly signed production app. This template deliberately has **no debug App Check bypass**. For private integration testing you would need to add a separately provisioned debug provider/token in a development-only variant; never embed that token in a distributed APK. Enable Firebase App Check enforcement for RTDB after confirming client access. Backend verification is always on.
2. Create a private GCS bucket with uniform bucket-level access, **no public access**, and a lifecycle rule removing `jobs/` objects after 24 hours. Grant the backend Cloud Run service account access to create/read stage objects and to sign short-lived V4 PUT URLs (`iam.serviceAccounts.signBlob` / Service Account Token Creator on the signing identity as required). Grant the **separate builder** service account object-viewer access to the bucket. Give the builder a JSON credential only in GitHub Actions secrets; do not bundle it into Android.
3. Choose a private Google Drive folder. For a Workspace **Shared Drive**, grant the backend and builder service account access to the folder. For a personal My Drive, use a properly authorized OAuth refresh token belonging to the storage owner; configure `DRIVE_CLIENT_ID`, `DRIVE_CLIENT_SECRET` and `DRIVE_REFRESH_TOKEN` as **backend runtime secrets and builder Actions secrets**. Service accounts generally cannot own files in personal My Drive (they have no personal storage quota). Do **not** grant `anyoneWithLink` permissions; the backend validates the Drive parent before issuing download claims. Configure a Drive retention policy separately.
4. For the existing `SaifAI-Builder` repository, **fix and merge draft PR #2 first**: its `.github/workflows/build.yml` must read objects by `assetId`, upload an actual APK/ZIP/MP4 with the exact Drive MIME, and build real artifacts instead of placeholders. Configure that workflow's Actions secrets `GCP_CREDENTIALS`, `GDRIVE_FOLDER_ID`, `WORKER_CALLBACK_SECRET`, and `SAIF_GCS_BUCKET` / `SAIF_CLOUD_API_BASE_URL` as secrets or variables; the bucket, folder and callback key must match backend `STAGING_BUCKET`, `DRIVE_FOLDER_ID` and `WORKER_CALLBACK_SECRET` respectively. Do not move their values into chat or source. If you instead **replace** the existing worker with all of `builder-template/` (including `.github/workflows/saif-cloud-build.yml` and its `apk-template`/scripts/package files), set backend `BUILDER_WORKFLOW=saif-cloud-build.yml` and configure the template's **different** Actions names `GCP_SERVICE_ACCOUNT_JSON`, `STAGING_BUCKET`, `DRIVE_FOLDER_ID`, `WORKER_CALLBACK_SECRET`, optional `GEMINI_API_KEY`, and `CLOUD_API_BASE_URL`; do not mix the two workflows' names. The template uses a vetted fixed Gradle project and checks its compiler mirror digest, but is not a complete sandbox for untrusted build/media inputs. Either workflow must be present on the configured default ref and accept `job_id`. Give the backend a dedicated fine-grained **server-side** GitHub credential with Actions:read/write for the builder repo only, in runtime secret `GITHUB_DISPATCH_TOKEN`; never put it into Android `BuildConfig` or a public repo. Anyone who can edit the worker or read its Actions secrets is in the trust boundary; use a separate network-restricted sandbox for an open public service.
5. Deploy `backend/` to an HTTPS Cloud Run service with a public **HTTP entry point** for the website and Firebase/App Check verification on private API calls (e.g. `gcloud run deploy saif-downloads --source cloud/backend --region REGION --service-account BACKEND_SA --timeout=1800 --set-env-vars ... --set-secrets ...`, with invoker access configured so browsers can open public download pages). `backend/.env.example` names every runtime variable. Set `FIREBASE_ANDROID_APP_ID` to the exact Firebase Android app ID (the `mobilesdk_app_id` in the downloaded `google-services.json`), so a token from a different app in the same project cannot dispatch. The container starts with `npm start` on port `8080`. **Never commit live `.env` values or run the example placeholders as secrets.** Add WAF/Cloud Armor or equivalent IP/budget throttling for anonymous clients in addition to the backend's per-UID hourly limit. Use an HTTPS custom domain for **your website**; route `/download/:jobId`, `/api/*`, `/static/*` and `/` to this gateway on the **same origin** (or provide an equivalent same-origin reverse proxy). Set the portal URL to that website hostname, not a Drive or GitHub hostname. Verify `/healthz`, `/`, and `/download/<valid-job-uuid>` via your deployed hostname. The sponsor block is a **placeholder only**; any later real ad scripts need a privacy review because a download claim is present in the browser's page fragment.
6. In **this Android repository's Actions variables** (preferred) set `SAIF_CLOUD_API_BASE_URL=https://<your-site-host>`, `SAIF_DOWNLOAD_PORTAL_URL=https://<your-site-host>` (the site's reverse proxy must serve the backend's `/api/*` and `/download/:jobId` on this origin), and `SAIF_FIREBASE_DATABASE_URL=https://<your-rtdb-host>`. If these public origins were already stored under the **same names** in this repository's Actions **secrets**, the APK workflow also accepts those as a fallback; the Builder repository's settings are separate and do not flow into this APK. When all three origins are present, CI probes gateway `/healthz`, unauthenticated `/api/push` denial and the portal's invalid-claim route **without credentials or uploaded bytes**, and refuses to publish a purportedly connected APK if the configured site is only a demo or login redirect. This is a route preflight, **not** a real upload test. Rebuild and test a device-signed APK after deployment. The URLs are public **addresses**, not credentials. App sign-in remains email/password or guest; Antigravity OAuth remains a **separate in-app** connection.
7. The **Software Updates** control checks `https://<your-site-host>/version.json` and will report *not configured* until you publish one. If you choose to publish app updates, host a properly signed, compatible APK on **the same website** and a version feed with `package_name` (the Android application ID), `version_code`, `version_name`, `download_url` (full HTTPS URL to that site's `.apk`), and optional `changelog`/`is_critical`. The Android updater rejects off-site URLs and redirects. This public app-updater feed is **separate** from private, one-time generated-file links. Do not point it to a private GitHub release or an unsigned/differently signed debug APK. Your website must host this feed and APK; the template does not deploy them for you.

## What the example builder does—and doesn't

- Existing SAIF AI Project Studio text sources/resources (including its `AndroidManifest.xml`) are staged as bounded UTF-8 JSON; media/fonts are streamed as private binary objects. Project-supplied Gradle files are never accepted. A fixed, non-overridable Gradle build (AGP 9.0.1 / Android 35) builds a **debug APK**. Starter Studio sources use platform Android APIs; if edited source needs external libraries, a maintainer must add vetted dependencies to the fixed builder template—uploaded Gradle files cannot do so. If the project is only a prompt, `GEMINI_API_KEY` is required to produce an offline WebView HTML app. No model is silently assumed. The template does **not** produce a stable production signing key, a Play Store release, or guaranteed fully functional generated games. Each runner's debug APK may use a different signing key; uninstall an older generated app before installing a newer debug build with the same package name. Configure your real builder and signing infrastructure before making production promises.
- Video Studio text, media clips, images, audio and voice audio are rendered by FFmpeg in Actions; the selected resolution, frame rate and bounded bitrate tier are sent with the job. **HTML/code scenes are represented by their title cards, not animated pixel-perfect Studio output**, and generated voice text without an audio asset appears as text. Prompt-only videos require `GEMINI_API_KEY` for a storyboard and are text-card videos unless you add a full media generator. These limitations are explicit to avoid pretending an untested template is the final video production backend. A more capable renderer can replace `builder-template/scripts/render_video.py` without weakening the private gateway.
- One **build** asset is capped at 100 MB, a build job at 20 assets/300 MB, input source text at 1.5 MB, a separate user-uploaded file at 300 MB, and a delivered APK/ZIP/MP4 at 2 GB. Video Studio jobs with a selected bitrate that projects over 2 GB are rejected up front; lower the bitrate or shorten the video. The Android chat still displays text/code/small images inline **below** 3 MB (small chat image attachments may use the model's normal inline encoding; **build inputs never use the former Base64 archive upload**). Local APK compilation and full timeline rendering are no longer invoked from the app's build/export buttons. The pre-existing on-device compiler implementation remains in the tree for legacy tests/utilities but is not an app build route.
- One active job is shown on the current device; the last job can be restored after restart if the same Firebase identity is available. Local/guest cloud jobs use an **ephemeral Firebase Anonymous UID**. Signing out revokes it: their old jobs cannot be reopened or have links refreshed after sign-out/reinstall. Download the file first, or use a persistent Firebase email/password account. Account sign-out clears the visible job; the portal has **no public file listing**.

## Portal deployment

The portal (`portal/`) is deployed to AI Studio as a separate project. It can run in two modes:

**Demo mode** (no environment variables): Serves a self-contained demo vault. Use this for development, previews, and the public download page when no gateway is configured.

**Production mode** (`SAIF_CLOUD_API_BASE_URL` set): Proxies vault queries and one-time claim downloads to the gateway at that URL. The portal's `/api/vault/:vaultId` endpoint calls the gateway's `/api/inspectDownload`, and `/api/vault/:vaultId/ad-complete` calls `/api/claimDownload` to stream the actual file from private Drive.

### To deploy the portal in production mode on AI Studio:

1. Open the AI Studio project at `https://saifai-downloads.ai.studio/`
2. Go to **Settings → Environment variables**
3. Add `SAIF_CLOUD_API_BASE_URL` = your gateway's HTTPS URL (e.g. `https://saif-downloads-xyz.run.app`)
4. Redeploy — the portal will now proxy to the gateway

### Portal endpoints:

| Route | Method | Purpose |
|-------|--------|---------|
| `/healthz` | GET | Liveness check for CI preflight |
| `/api/inspectDownload` | POST | Proxy to gateway for preflight compatibility |
| `/api/vault/:vaultId` | GET | List vault files (demo or proxied) |
| `/api/vault/:vaultId/ad-complete` | POST | Complete ad and download file |
| `/api/vault/:vaultId/rotating-status` | GET | Rotating ad status |
| `/api/push` | POST | 501 in production (gateway-only) |
| `/api/trigger-build` | POST | 501 in production (gateway-only) |
| `/api/firebase-latest` | GET | Firebase config proxy |

## Test the template

The `Verify SAIF AI cloud builder template` workflow compiles a sample isolated debug APK and renders a short text/image/audio MP4 on a clean Actions runner. This is a build/render smoke test, **not** a live Firebase, GitHub dispatch or private Drive integration test.

```sh
cd cloud/backend && npm ci && npm test
cd ../portal && npm ci && npm test
cd ../builder-template && npm ci && npm test
python3 -m unittest discover scripts -p 'test_*.py'
```

These tests exercise path validation, private-claim semantics, auth/App Check gates, owner isolation and mocked Drive streaming, as well as the builder's fixed-source preparation and FFmpeg command construction. They do **not** prove a live Drive upload, GitHub dispatch, Play Integrity verification, or an Android APK built in the **separate** builder repo. Run an end-to-end deployment test with credentials that you configure outside the source tree. Keep the existing GPLv3 license and third-party notices for covered code.
